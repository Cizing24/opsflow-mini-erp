# 技術重點與工程挑戰

## 可展示的實作

- **狀態與授權一起驗證**：前端角色顯示加上後端 RBAC、工程師 membership、同部門簽核及禁止自簽；不是只隱藏按鈕。
- **核准競態的實際修復**：獨立 review 找到舊明細核准問題，先以 MySQL 等鎖測試重現，再修正鎖順序，保留 RED/GREEN。
- **收貨與領料一致性**：同 Key 8 請求只入庫一次；不同 Key 超收競爭與 12 人搶最後一件有真實資料庫驗證。
- **公開資料來源管理**：處理 UCI 官方 541,909 列，僅保留 100 個商品目錄衍生品項，清楚區分公開欄位、合成成本與模擬企業交易。
- **實測而非漂亮數字**：100,706 筆異動的 API 分位數、throughput、error rate、SQL EXPLAIN、索引前後及深頁成本均附環境與 commit。
- **維護交付**：Migration 失敗與前向修復、回歸 mutant、供應商 timeout、備份還原、Docker app 實際登入，以及 GitHub CI。

## 面試時可以深入說明

先問清楚交易的不可變條件：一張請購只轉一張 PO、receivedQty 不可超過 quantity、Stock 不可負數、成本不可重複認列。再說明鎖、unique constraint、條件 UPDATE 與 transaction 各自保護哪個條件。

用 Issue #5 說明「有 transaction 不代表沒有 race」：如果在拿鎖前讀取決策依據，仍可能用舊資料核准新狀態。用 Issue #4 說明「匯入程式成功不代表資料筆數正確」：必須比對來源、清洗結果與 DB counts。

成本採固定標準成本，周轉率缺少估值快照時回 null。這些界線應直接說明，不能把未實作功能包裝成架構優勢。
